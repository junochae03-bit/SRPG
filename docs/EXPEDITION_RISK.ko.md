# 지역별 위험 원정

2026-09-13. Stoneshard 선택 항목 SE08의 구현이다. 맵을 넓히지 않고 같은 경로에서 증원과 보상을 선택한다. 이 기능의 검증을 탐사 재미나 벤치마킹 전체 완료로 간주하지 않는다.

## 플레이 흐름

원정의 문에서 층과 `안정 · 경계 · 험지 · 극한`을 선택한다. 첫 10층과 모든 10층 단위 레이드는 안정으로 고정한다. 11~30층은 경계, 31~60층은 험지, 61~100층의 일반층은 극한까지 열린다.

위험 한 단계마다 다음을 적용한다.

- 증원 2마리: 수문장 접근로부터 시작하고, 추가 단계는 선택 곁방에 배치한다. 해당 지역의 원거리·지원과 전열 조합을 사용한다. 극한의 마지막 증원은 지역 정예 종류다.
- 적 기본 체력 +10%: 그 뒤 별도로 파티 인원 보정을 적용한다. 재계산으로 보정이 중첩되지 않는다.
- 기본 드랍 확률의 상대 배율 +0.15: UI는 `×1.15`, `×1.30`, `×1.45`로 표시한다. 희귀도나 레이드 전용 등급을 바꾸지 않는다.
- 수문장 처치 시 플레이어별 정수 +2: 기존 개인 전리품과 중복 처치 방지 경로를 사용한다.

일반층의 지형·시야 환경·기존 배치와 스폰/출구 여유 공간은 유지한다. 시드는 증원 위치와 조합을 재현한다. 원정 중 위험을 낮출 수 없고, 다음 일반층에 이어진다. 레이드층에서는 실제 위험을 0으로 적용한 뒤 다음 일반층에서 선택을 복원한다. 마을 귀환 시 초기화한다.

## 협동과 저장

마을의 방장만 출발 조건을 변경한다. 변경 때 전원 준비를 해제한다. 준비 요청에 보이는 선택의 변경 번호를 포함하고, 이전 번호로 들어온 준비는 거절한다. 원정의 문과 별도 협동 방 화면 모두 층·위험·효과·보상을 보여 준다. 참가자의 개인 탐사 목표는 공유 출발 조건과 별개다.

출발 전 저장에 실패하면 원래 맵과 선택을 보존한다. 위험은 개인 캐릭터 성장이나 저장 파일에 추가하지 않는 원정 상태다. 저장 형식은 7, 협동 프로토콜은 7이다. 프로토콜 6 클라이언트는 참가 단계에서 거절한다.

## 근거와 한계

구현: `expedition_risk.gd`, `dungeon.gd`, `simulation.gd`, `local_session.gd`, `coop_session.gd`, `town_panel.gd`, `expedition_brief_panel.gd`, `coop_panel.gd`.

모델은 100층 상한·시드 재현·안전한 배치·보정 분리·조건 변경·저장 실패·실제 처치 보상·레이드 경계를 검사한다. 시각 검사는 1920×1080에서 지역별 버튼·층 제목 실제 표시·6인 준비·별도 방 화면·실제 입장을 검사한다. 6개 실제 ENet 프로세스로 선택 공유·오래된 준비 거절·위험 배치 재구성·인원 보정을 확인했다. 전체 검사 결과와 해시는 `docs/qa/expedition-risk-verification.json`에 기록한다.

QA팀의 층 제목 누락과 준비 화면의 조건 요약 부족 지적을 수정하고 실제 캡처로 재확인했다. DB에는 `metadata.expedition_risk`와 계산 근거 `metadata.expedition_risk_source_rules`를 추가했다. 기존 DB 관리 작업으로 인계한다.

외부 회선 6인 장시간 밸런스와 실제 탐사 재미 평가는 미확인이다. 특히 발견·경로 선택·불필요한 왕복 감소는 위험 수치 추가와 별도로 확인해야 한다. 이후 탐사 개선은 맵 면적 확대보다 갈림길의 단서, 구역마다 갈 이유, 보상 뒤 전진 합류의 실제 이동 비용을 기준으로 삼는다. 모든 곁방을 정리하도록 강제하지 않는다.

최종 전체 검사: **137개 그룹 / 532,917개 검사 PASS**, `runtime/v01-checks/20260913-075230`. 실행 파일 384개의 해시가 일치한다. 첫 전체 실행은 기존 아이콘 테스트가 선택한 층과 다른 100층으로 직접 입장하려 해서 실패했다. 해당 테스트를 실제 층 선택 절차에 맞게 수정한 뒤 처음부터 다시 통과한 결과다. 후반만 실행한 진단 결과를 전체 통과로 합산하지 않았다. 6인 ENet 검증은 `runtime/coop-check-1789252720999271000`이며 DB 관리가 정본 다섯 파일의 일치를 읽기 확인했다.
