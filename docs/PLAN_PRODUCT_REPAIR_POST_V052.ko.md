# V0.5.2 이후 제품 보수 계획

2026-09-10 QA팀 지시를 반영한다. 기준 실행 파일은 V0.5.2, 태그 커밋은 `5eecdba4dc9a9f86ef4088baf592433050035add`다. 이번 문서는 후속 작업의 순서와 완료 기준이며, 아래 플레이 평가를 이미 수행했다는 뜻이 아니다.

총괄은 원인 재현·수정·통합과 엔진의 순차 실행을 담당하고, QA팀은 코드와 경험별 증거를 검토한다. DB 원본·스키마·생성 결과의 변경은 DB 관리에 인계한다. 취향처럼 사용자의 판단이 필요한 선택은 보류하되, 검증과 필요한 결함 수정은 기존 승인 범위에서 진행한다.

새 콘텐츠 대량 추가, 온라인 멀티플레이, 별도 제작 중인 자산의 일괄 적용은 이번 보수 범위에서 제외한다. 현재 게시된 V0.5.2 태그와 배포 파일은 기준본으로 보존한다. 자동 검사 수나 콘텐츠 수를 제품 완성도 점수로 환산하지 않는다.

## 우선순위와 상태

| 순서 | 대상 | 현재 상태 | 다음 단계로 넘어갈 근거 |
|---|---|---|---|
| 1 | 새 기록의 첫 30분 | 실행 대기 | 목표 발견·장비 비교·성장 선택·전직 경로·실패 후 복귀에서 막힌 순간과 수정 전후 차이를 QA팀에 전달 |
| 2 | 도감 최초 열기 지연 | 짧은 표본 약 0.7초, 원인 분리 대기 | 첫 열기와 재열기를 같은 조건에서 계측하고 입력·화면 정지의 원인과 개선을 확인 |
| 3 | 빌드와 대표층의 전술 차이 | 비교 플레이 대기 | 같은 투자량의 두 빌드와 대표층 세 곳에서 위치·자원·기술 선택의 실질적 차이를 기록 |
| 4 | 60분 실전 성능 | 장기 실행 대기 | 실제 창에서 구간별 프레임 분포와 메모리 추세, 저장·재진입 결과를 확인 |

각 단계는 결과와 코드 변경을 QA팀에 전달하고 차단 결함을 처리한 뒤 다음 단계로 진행한다. 별도 사용자 승인 절차는 추가하지 않는다. 취향 결정이나 실제 신규 사용자 참여가 필요한 평가는 그 부분만 미확인으로 남긴다.

## 1. 첫 30분의 이해와 조작

캐릭터 생성부터 정상 진행한 새 기록으로 검사·궁수·마법사의 흐름을 확인한다. 기존 개인 기록과 100레벨 시험 기록을 사용하지 않는다. 시간은 캐릭터 생성부터 기록하며, 관찰 중 레벨·재화·장비를 보충하지 않는다.

목표를 처음 발견한 시점, 첫 장비의 비교·착용, 첫 성장 포인트 투자, 전직 조건과 경로를 찾는 과정, 전투 실패 후 복귀를 기록한다. 막힌 위치, 잘못 누른 동작, 필요한 설명과 다시 시도한 횟수를 화면·입력 시각과 연결한다. 30분 안에 전직까지 도달하지 못하면 전직 완료를 검증했다고 쓰지 않는다. 의도적으로 만든 실패 상황은 정상 진행 관찰과 별도로 표시한다.

수정 대상은 관찰 결과에 따라 `title_screen.gd`, 캐릭터 생성 화면, `inventory_panel.gd`, `skill_tree_ui.gd`, `npc_dialogue.gd`, 마을·진행 화면 중에서 한정한다. 설명 문장을 늘리는 것을 기본 해결책으로 삼지 않는다. 다음 행동의 선택과 결과가 보이는지 확인한다.

증거는 세 직업의 시각별 관찰 기록과 막힌 장면의 수정 전후 화면이다. 에이전트의 조작 결과와 실제 신규 사용자의 이해도는 구분한다. 변경에 맞는 기존 회귀를 실행하고 배포 후보를 만들 때 `python tools/verify_v01.py`로 전체 원본을 확인한다.

## 2. 도감 첫 열기

기존 측정은 [짧은 처리 시간 보고서](PERFORMANCE_V052.ko.md)를 따른다. 게임 프로세스를 새로 시작한 첫 열기와 같은 프로세스의 재열기를 구분하고, 운영체제 파일 캐시까지 초기화했다는 주장은 별도 근거 없이 하지 않는다.

기존 측정 진입점은 `python tools/profile_client.py --save <검사용_기록.json> --label codex-baseline --menu codex`다. 이 명령은 기록의 복사본을 사용하며 현재 짧은 측정만 지원한다. 재열기·입력 응답·실제 화면의 첫 그리기 시각은 측정 도구에 추가해야 한다. 새 측정 경로를 만들고 동작을 확인하기 전에는 재열기와 입력 지연의 결과를 채우지 않는다.

DB 질의, 데이터 정리, 아이콘 준비, 목록 컨트롤 생성, 첫 화면 표시를 나눠 측정한다. 같은 장치·해상도·렌더러·수직 동기화·프레임 제한과 기록으로 수정 전후를 비교한다. 목록 표시를 늦추는 변경은 로딩 중 선택과 입력 처리, 검색·탭 전환, 닫기·재열기에도 일관된 결과를 내야 한다. 총 처리 시간만 줄고 화면 정지가 남으면 완료로 판단하지 않는다.

수정 후보는 도감 화면, `game_database.gd`, 자산 조회와 측정 도구다. 원인 측정 전 일괄 비동기화나 전체 데이터 상주를 결정하지 않는다. 관련 회귀와 실제 실행 화면을 QA팀에 전달한다.

## 3. 빌드 두 종류와 대표층 세 곳

같은 직업·레벨·장비·투자한 스킬 포인트를 기준으로 선택 경로만 다른 두 빌드를 만든다. 비교용 기록을 준비한 사실과 조건을 명시하고 첫 30분의 정상 성장 기록과 섞지 않는다.

일반 무리, 넓은 교전 또는 위치 제약, 보스·무력화처럼 다른 판단을 요구하는 대표층 세 곳을 실제 관찰 후 확정한다. 수정 전후에는 같은 지도 시드·적 배치와 장비 조건을 사용한다. 처치 시간뿐 아니라 접근 경로, 공격 방향, 안전 위치, 자원 사용, 기술 선택을 영상 또는 시각이 있는 행동 기록으로 비교한다.

피해량 숫자만 다른 두 빌드는 차별성이 입증됐다고 쓰지 않는다. 유효한 선택이 생기는 조건과 약해지는 조건을 함께 남긴다. 관찰에 필요한 범위에서 직업·스킬·몬스터·던전을 수정하고 변경된 수치와 규칙은 DB 관리에 전달한다. QA팀은 수치와 플레이 방식의 변화를 구분해 검토한다.

## 4. 실제 60분 성능

앞선 단계의 배포 후보를 실제 표시한 창으로 60분 실행한다. 현재 12초 측정 도구를 반복한 결과로 대신하지 않는다. 이동·다수 적 전투·스킬·가방·도감·마을·저장·종료 후 재진입을 포함하는 순서를 먼저 정하고 구간 시각을 기록한다.

프레임 시간의 p50·p95·p99와 가장 긴 지연, 메모리의 시간별 추세를 구간마다 기록한다. 장치, 클라이언트 해상도, 그래픽 설정, 창의 포커스, 적 수와 효과 수를 함께 남긴다. 로딩과 실제 교전의 분포를 따로 보관하고 평균 하나로 합치지 않는다. 소리 중첩·장면 이동·메뉴 반복 뒤의 잔류 객체와 메모리 증가도 확인한다.

저장은 성공 표시뿐 아니라 재진입 후 주요 진행·장비·재화가 일치하는지 검증한다. 발견한 증가 추세와 멈춤은 재현 절차·로그·수정 전후로 QA팀에 전달한다. 실제로 완료한 시간과 구간만 기록한다.

## 결과 인계

단계별 보고에는 기준 커밋과 실행 파일 해시, 조건, 관찰한 문제, 수정한 범위, 실제 실행한 검사 명령, 수정 전후 증거와 남은 한계를 담는다. 개인 기록과 원본 영상·로그는 공개 소스에 넣지 않고 필요한 요약만 선별한다. QA팀이 검토할 수 있는 증거를 먼저 전달한 뒤 제품 평가 갱신을 요청한다.
